Message ownership and memory choices

English | 简体中文

For applications choosing how long message bytes must remain valid. Start with owned results; use other delivery forms when buffer reuse, synchronous processing or retained sharing fits the workload. Access order is a separate choice.

Choose by lifetime

Need Choice Main cost or obligation
Keep or modify independent results ReadMessages() Allocates independent result objects and copies payloads and mutable declarations
Reuse application storage ReadNext(buffer, ...) Copies into caller storage; grow the buffer when required
Process bytes before returning ReadNext(visitor) / VisitMessages Borrowed spans expire on callback return; no reader reentry
Retain or forward shared bytes ReadBatchLease Lease control objects may allocate; backing storage stays alive until all owners release it

Borrowing grants temporary access without ownership. A storage lease retains immutable backing storage, possibly a whole chunk or mapping. Neither choice makes memory usage proportional only to selected payload bytes. Consult reader availability and contracts before selecting a delivery form.

Reuse caller buffers

This loop uses the path from the tutorial:

using var session = new McapReaderFactory(path).OpenMessages();
byte[] buffer = [];
while (true)
{
    var status = session.ReadNext(buffer, out var header, out var length);
    if (status == McapReadStatus.EndOfStream) break;
    if (status == McapReadStatus.BufferTooSmall)
    {
        buffer = new byte[checked((int)length)];
        continue;
    }
    Console.WriteLine($"{header.LogTime}: {System.Text.Encoding.UTF8.GetString(buffer, 0, checked((int)length))}");
}

An insufficient buffer leaves the same message pending for retry. Process successful bytes before reusing the buffer; empty messages are successful results, not EOF. The library's warmed caller-buffer path allocates 0 B managed, but this demonstration allocates when growing the buffer or formatting output. It still copies payload bytes. See buffer contracts.

Borrow for immediate processing

using var borrowed = new McapReaderFactory(path).OpenMessages();
borrowed.VisitMessages((in McapMessageHeader header, ReadOnlySpan<byte> payload) =>
{
    Console.WriteLine($"{header.LogTime}: {payload.Length} bytes");
    return true;
});

Use the span only inside the callback. Do not read, inspect or dispose the same reader from that callback. Returning false stops normally after the current message. Snapshot callbacks impose additional restrictions on indexed readers and prepared indexes; see borrowing contracts.

Retain only what the application needs

For short pipelines, keep a batch lease alive through processing and dispose it afterward. A lease survives reader advancement, reader disposal and cache eviction. For a small payload kept much longer, copy it explicitly:

using var retained = new McapReaderFactory(path).OpenMessages();
byte[]? savedPayload = null;
using (var batch = retained.ReadBatchLease(1))
{
    if (batch is not null)
    {
        savedPayload = new byte[batch.GetPayload(0).Length];
        batch.CopyTo(0, savedPayload);
    }
}
// savedPayload is independent of the lease and reader.

Copying releases no storage still referenced by another lease, parser or cache. Bound outstanding work using retained backing sizes and duration as well as batch counts. Do not access spans concurrently with lease disposal; cross-thread transfer needs caller synchronization. See retention contracts.

To forward a batch, register destination schemas/channels first, then call writer.WriteBatch(batch) while the lease is alive. Use the header-replacement overload when channel IDs differ. Forwarding is synchronous, does not transfer ownership and does not make a batch atomic. The runnable example demonstrates a schema-less channel with matching IDs.
